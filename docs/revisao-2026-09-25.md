# Revisão dos scripts — 25/09/2026

Foram revisados os scripts Python, os testes, as dependências, os READMEs e as
chaves de configuração de `config/local/env.txt`. Configurações existentes foram preservadas.
Nenhum comando de migração/validação foi executado nas VMs ou no BigQuery.

## Problemas identificados e corrigidos

| Problema | Consequência anterior | Correção |
|---|---|---|
| Descoberta por `information_schema.tables` | Views materializadas não entravam no inventário; objetos sem privilégios podiam desaparecer | Catálogo `pg_class` compartilhado e colunas de `pg_attribute` |
| Normalização diferente entre scripts | Destino existente podia ser reportado como ausente, especialmente com acentos | Mesma função de nomes, preservando a convenção histórica da migração |
| Nomes distintos com mesmo destino normalizado | Uma tabela podia sobrescrever outra | Verificação de colisões antes da carga e erro no relatório de validação |
| Falha ao listar um banco | Validação abortava antes de gerar o relatório dos demais | Linha de erro por banco e continuação |
| Reenvio de job com ID novo | Lote/cópia em append podia ser executado duas vezes | IDs estáveis por operação; recuperação do job em caso de conflito |
| Checkpoint antigo ou de outro contexto | Tabela podia ser ignorada indevidamente | Contexto, alias e existência do destino verificados; nova rodada limpa os registros antigos |
| Tamanho excedido e seleção vazia | Execução podia terminar com sucesso apesar de omissões | Código de saída de falha |
| JSON escalar | Strings, números e booleanos podiam falhar ou mudar de interpretação | Uso dos valores já decodificados por psycopg2 |
| Numeric considerando apenas precisão total | Falha de carga ou arredondamento por escala incompatível | Limites de parte inteira/escala; STRING quando não há representação garantida |
| Geometria com Z/M | WKT incompatível com carga GEOGRAPHY | Conversão explícita para 2D |
| Context manager de psycopg2 | Conexões permaneciam abertas | Fechamento explícito |
| Timeout após rollback | Limite desaparecia para tabelas seguintes | Reaplicação por tabela |
| Estatísticas ausentes e views no modo metadata | Zero estimado podia parecer validação bem-sucedida | Rejeição de estimativas indisponíveis; ESTIMATE_MATCH nunca é validação exata |
| Parquet com inteiros nulos/muito grandes | Inferência float podia perder precisão; tipos variavam | Tipos explícitos e escrita atômica |
| Arquivos de exemplo citados, mas ausentes | Instalação documentada não podia ser seguida | Exemplos sem credenciais incluídos |

## Aplicação nas VMs

1. Faça backup dos scripts atuais.
2. Copie o conteúdo do pacote para `/opt/migracao`, incluindo o novo módulo
   `migration_common.py`. O pacote não contém `.env`, `config/local/env.txt`, chaves ou checkpoints.
3. Preserve o ambiente virtual existente. Se ele se chama `.venv-new`, adapte os
   comandos dos READMEs; não é necessário recriá-lo só para mudar o nome.
4. Instale `requirements-validation.txt` nesse ambiente para usar a validação
   e todos os testes. Confira projeto, região, porta PostgreSQL e filtros da VM.
5. Crie os diretórios de saída com dono `postgres`, conforme README, e configure
   o checkpoint em `/opt/migracao/state/migration-checkpoint.json`.
6. Execute os testes e `migrate.py --inventory`. Execute a validação exata com
   `--fail-on-difference` para identificar os destinos ausentes/divergentes.
7. Revise o relatório antes de recarregar dados. Checkpoints da versão anterior
   exigem iniciar uma nova rodada sem `--resume`.

## Limites restantes

- Não é possível atribuir a causa das tabelas ausentes nas VMs sem seus
  inventários, configurações efetivas, logs e relatórios. Os problemas acima são
  evidências no código, não confirmação do que ocorreu em cada VM.
- A validação compara contagem, nomes e tipos; não faz comparação linha a linha.
- Alterações na origem após a migração podem causar divergências legítimas.
- A descoberta cobre somente os bancos da instância/porta configurada; VMs com
  mais de uma instância precisam executar uma rodada por porta.
- Em append, uma queda entre publicação e checkpoint pode exigir reconciliação
  manual antes de reexecutar. IDs estáveis protegem as tentativas da mesma
  operação, não uma execução nova após reiniciar o processo.
- Não execute duas migrações simultâneas para o mesmo destino/checkpoint.
- `numeric` sem limites passa a STRING. Isso evita perda de precisão, mas pode
  exigir ajustes de consultas no destino e pode impedir append em schemas antigos.
- O limite de tamanho usa tamanho físico: views/foreign tables e pais
  particionados não refletem necessariamente o volume do resultado lido.
- Logs e Parquet são locais; a publicação em GCS/BigQuery depende da configuração.

Referências técnicas: [catálogo PostgreSQL](https://www.postgresql.org/docs/17/catalog-pg-class.html)
e [identificação de jobs BigQuery](https://docs.cloud.google.com/bigquery/docs/running-jobs).
